1. Executive Summary & Core Problem Statement

Modern mobility platforms face distinct engineering bottlenecks: traditional fixed-price hailing (e.g. Uber/Rapido) lacks dynamic peer-to-peer price discovery, while pure bidding apps (e.g. inDrive) often suffer from race conditions and broadcast storms under dense demand. Furthermore, urban commuters lack unified access to long-distance highway carpooling.

RideX unifies intra-city bike/auto/cab booking, inDrive-style dynamic fare negotiation, and highway corridor carpooling into an event-driven, ACID-compliant architecture. The system is engineered to handle 1,000,000 peak concurrent drivers, ingesting over 333,000 GPS telemetry updates/second with sub-100ms dispatch latency.

5. Core Algorithms & Concurrency Handling

5.1 inDrive Bidding Protocol & Race Condition Prevention

When multiple drivers accept a passenger's offer simultaneously, RideX enforces Atomic Conditional Mutation:

UPDATE rides SET driver_id = $driverId, agreed_fare = $price, status = 'ASSIGNED', updated_at = NOW() WHERE id = $rideId AND status = 'BIDDING';

The first transaction acquires the row lock and mutates status to ASSIGNED (rows_affected = 1). Competing transactions evaluate WHERE status = 'BIDDING' on the updated row, fail the condition (rows_affected = 0), and return an immediate 409 Conflict. In multi-instance clusters, this is guarded by a Redis Redlock distributed mutex on ride_id.

5.2 Geospatial Indexing: Uber H3 vs. Square Grids (Geohash)

  • Neighbor Distance Equidistance: In square grids, diagonal neighbors are $\sqrt{2} \times d \approx 1.414d$ (41.4% farther away), creating severe directional distortion during nearby driver queries. In an Uber H3 Hexagon, all 6 neighboring cells are equidistant ($1.0d$). There are no diagonals and zero directional bias.
  • Circular Approximation: Hexagons maximize the area-to-perimeter ratio, providing the closest tessellating approximation to a real-world circular search radius.
  • Resolution 8: Average edge length is ~461 meters. A 3 km radius query executes an in-memory k-ring(3) query (37 cells total) in <0.5 ms in Redis.

5.3 Intercity Carpool Corridor Buffering (PostGIS ST_Buffer)

  • Corridor Generation: The driver's intercity road vector polyline $R$ is expanded into a 5,000-meter spatial polygon:
    Corridor = ST_Buffer(R, 5000);
  • Waypoint Validation: A passenger ride request is matched if and only if both pickup and drop-off coordinates are inside the corridor:
    ST_Contains(Corridor, P_pickup) AND ST_Contains(Corridor, P_drop) = TRUE;
  • Seat Overbooking Prevention: Handled via atomic SQL decrement:
    UPDATE carpools SET available_seats = available_seats - $seats WHERE id = $id AND available_seats >= $seats;

6. Real-Time Telemetry & WebSocket Ingress Gateway

  • Protocol Justification: WebSockets eliminate 800-byte HTTP header overhead per ping, reducing network bandwidth by over 90% with 2-byte frame overhead.
  • Room-Based Pub/Sub (subscribe_ride): Location telemetry for Ride #101 is delivered exclusively to authorized subscribers of #101 ($O(1)$ delivery vs $O(N)$ global broadcast storm).
  • Thundering Herd Mitigation: Heartbeat ping/pong every 30s prunes dead sockets. Exponential backoff with randomized jitter ($1s \to 2s \to 4s$) prevents server crashes during gateway recovery.
  • Anti-Spoofing & Boundary Validation: Validates $-90 \le \text{lat} \le 90$, $-180 \le \text{lng} \le 180$, and verifies that the transmitting user possesses the driver role and is assigned to the active ride.

7. Security, RBAC & Double-Entry Financial Ledger

  • Password Security: Passwords salted and hashed with bcrypt (work factor 10). Plaintext passwords never exist in database records, API responses, or logs.
  • Stateless JWTs: HS256 signed tokens encoding user ID, email, and role claims (rider, driver, admin), enabling horizontal scaling without centralized session bottlenecks.
  • Object-Level Authorization: Enforces strict identity bindings (targetRide.riderId === req.user.id). User B cannot cancel, modify, or accept bids for User A's ride.
  • Double-Entry Accounting & Idempotency: Account balances are backed by an immutable ledger. Client-generated idempotencyKey UUIDs guarantee network retries never double-charge. Automated 85/15 driver payout and tip handling are enforced atomically upon trip completion.

10. Top System Design Viva Defense Questions

Q: Why Uber H3 hexagons instead of Geohash or QuadTree?
Answer: In Geohash (square grid), diagonal neighbors are $\sqrt{2} \times d \approx 1.414d$ (41.4% farther away), creating severe directional distortion during nearby driver queries. Uber H3's hexagonal grid ensures all 6 neighboring cells are exactly equidistant ($1.0d$). This eliminates directional bias and allows $O(1)$ in-memory radius searches via k-ring(3) in under 0.5 ms.
Q: How do you prevent double payment or double top-ups during network retries?
Answer: We enforce the Idempotency Pattern. Every financial request includes a unique client-generated UUID (idempotencyKey). The server checks if this key already exists in the immutable transaction ledger. If already processed, the server returns the existing transaction result immediately without re-debiting.
Q: How do you prevent a broadcast storm on your WebSocket gateway?
Answer: We use room-based topic filtering (subscribe_ride). When a driver streams GPS coordinates, the server broadcasts exclusively to clients subscribed to that specific rideId (the passenger). Updates are never broadcast globally to all connected clients.
