3. Team Roles & System Design Breakdown

Every team member owns a core pillar of the distributed architecture. Each role is balanced with explicit features, system design concepts, and a ready-to-speak viva introduction.

Member 1: Dynamic Bidding & Concurrency Architect
inDrive Bidding & State Machine

Primary Features Owned:

  • Dynamic inDrive Fare Negotiation: Passenger proposes fare (e.g. ₹50); nearby drivers receive offer and counter-bid (e.g. ₹60, ₹55).
  • Passenger Driver Selection: Side-by-side comparison of driver price, rating, vehicle model, and real-time ETA.
  • Ride Lifecycle Finite State Machine (FSM): Server-side state progression (REQUESTED → BIDDING → ASSIGNED → IN_PROGRESS → COMPLETED / CANCELLED).
  • Fare Estimation Rules: Vehicle-specific baseline calculations (Bike, Auto, Cab Economy, Parcel) based on road distance.

System Design Concepts to Defend in Viva:

  • Finite State Machine Integrity: Enforcing that state transitions are valid on the server. Invalid transitions (e.g., cancelling an already completed ride) are strictly rejected.
  • Atomic Concurrency Control: Preventing two drivers from claiming the same ride. Handled via atomic SQL conditional updates:
    UPDATE rides SET driver_id = $id, status = 'ASSIGNED' WHERE id = $rideId AND status = 'BIDDING';
  • Distributed Mutex (Redlock): In a multi-instance microservices tier, Redis Redlock locks the ride_id key during assignment.
  • Asynchronous TTL Expiry: Driver bids have a 25-second countdown timer; unaccepted bids auto-expire to free driver availability.

Member 2: Real-Time Telemetry & WebSocket Ingress Architect
Streaming Ingress & Pub/Sub

Primary Features Owned:

  • Live Driver GPS Tracking: Continuous transmission of driver coordinates, speed, heading, and remaining ETA.
  • WebSocket Gateway (ws://localhost:5000/ws): Low-latency, full-duplex persistent connection gateway.
  • Room-Based Pub/Sub Isolation (subscribe_ride): Delivering ride events exclusively to authorized subscribers.
  • Connection Lifecycle Management: Heartbeat ping/pong, exponential backoff reconnection, and driver GPS simulator.

System Design Concepts to Defend in Viva:

  • Protocol Trade-offs (WebSockets vs Polling vs SSE): WebSockets eliminate 800-byte HTTP header overhead per ping, reducing network bandwidth by over 90% with 2-byte frame overhead.
  • Preventing Broadcast Storms: Room isolation ensures Ride #101 events are published only to the authenticated driver and rider of #101 ($O(1)$ delivery vs $O(N)$ global flooding).
  • Thundering Herd Mitigation: Heartbeat ping/pong every 30s prunes dead sockets. Exponential backoff with randomized jitter ($1s \to 2s \to 4s$) prevents server crashes during gateway recovery.
  • Rate Limiting & Anti-Spoofing: Token bucket algorithm caps telemetry at 10 pings/sec; rejects coordinates from drivers not assigned to that ride.

Member 3: Geospatial Indexing & Carpooling Architect
Spatial Indexing & Route Corridor

Primary Features Owned:

  • Nearby Driver Discovery: Locating available drivers within a 3 km radius around the rider's pickup point.
  • Road Routing & Waypoint Geometry: OSRM road graph engine calculating true road paths and travel duration.
  • Intercity Carpooling (Publish & Browse): Scheduled highway carpool catalog with seat counts and custom driver pricing.
  • Carpool Corridor Route Matching: Matching riders traveling along an intercity highway route and reserving seats.

System Design Concepts to Defend in Viva:

  • Uber H3 Hexagonal Spatial Index: Why hexagons beat Geohash and QuadTrees: All 6 neighboring cells are equidistant from the center cell (unlike squares with $\sqrt{2}$ diagonal distortion). In-memory k-ring(3) lookup executes in under $0.5\text{ ms}$.
  • Spatial Corridor Buffering (ST_Buffer): The driver's intercity road vector polyline $R$ is expanded into a 5 km spatial polygon:
    Corridor = ST_Buffer(R, 5000);
    A passenger's ride is compatible if both pickup and drop-off points are inside the corridor:
    ST_Contains(Corridor, P_pickup) AND ST_Contains(Corridor, P_drop) = TRUE;
  • Inventory Concurrency: Overbooking is mathematically prevented using atomic conditional SQL decrements:
    UPDATE carpools SET available_seats = available_seats - $seats WHERE id = $id AND available_seats >= $seats;

4. Top 10 System Design Viva Questions & Direct Answers

Q1: "Why did you choose Uber H3 hexagons instead of Geohash or Google S2?"
Answer: In Geohash (square grid), diagonal neighbors are $\sqrt{2} \times$ farther than orthogonal neighbors, creating boundary distortion and directional bias. Uber H3's hexagonal grid has the unique property that all 6 neighboring cells are exactly equidistant from the center cell. This enables constant-time ($O(1)$) in-memory radius searches via k-ring(3) in under 0.5 ms.
Q2: "What happens if two drivers accept a dynamic bid at the exact same millisecond?"
Answer: We prevent double-assignment through atomic database conditional mutations: UPDATE rides SET driver_id = $id, status = 'ASSIGNED' WHERE id = $rideId AND status = 'BIDDING'. The database row lock ensures only the first driver succeeds (returning 1 affected row), while the second driver receives 0 affected rows and an immediate 409 Conflict. In a multi-node deployment, this is protected by a Redis Redlock distributed lock on the ride ID.
Q3: "Why WebSockets instead of HTTP Long Polling?"
Answer: HTTP Long Polling requires a full HTTP request/response handshake for every single location ping (~800 bytes of headers). At 333,000 pings/sec, HTTP headers alone would consume over 266 MB/s of bandwidth. WebSockets establish a single persistent TCP connection and transmit lightweight 2-byte frame headers, reducing network overhead by 90% and eliminating handshake latency.
Q4: "How do you prevent a broadcast storm on your WebSocket gateway?"
Answer: We use room-based topic filtering (subscribe_ride). When a driver streams GPS coordinates, the server broadcasts exclusively to clients subscribed to that specific rideId (the passenger). The update is never broadcast globally to all connected clients.
Q5: "How do you handle network disconnections and the Thundering Herd problem?"
Answer: On the server, heartbeat ping/pong every 30 seconds prunes half-open TCP connections. On the client, reconnection uses exponential backoff with randomized jitter ($1\text{s} \to 2\text{s} \to 4\text{s}$ up to $10\text{s}$). The jitter randomizes retry timings across reconnecting devices, preventing a recovering server from being overwhelmed by synchronized reconnect storms.
Q6: "How do you guarantee a user is never charged twice during a payment or top-up?"
Answer: We enforce the Idempotency Pattern. Every financial request includes a unique client-generated UUID (idempotencyKey). The server checks if this key already exists in the immutable transaction ledger. If already processed, the server returns the existing transaction result immediately without re-debiting.
Q7: "Why PostgreSQL over MongoDB for ride records and carpooling?"
Answer: Ride hailing and seat reservations require strict ACID transactional guarantees to prevent overbooking and phantom writes. PostgreSQL supports row-level locking (SELECT ... FOR UPDATE) and complex spatial polygon math via PostGIS (e.g. ST_Buffer and ST_Contains), which MongoDB cannot match natively with relational integrity.
Q8: "How does your system scale horizontally when user volume increases?"
Answer: We shard the database horizontally by city_id (Geographic Sharding). 99.9% of urban intra-city rides, driver queries, and bids occur entirely within a single city boundary, ensuring zero distributed cross-shard joins. For the WebSocket tier, stateless gateway nodes are coordinated across instances via a Redis Pub/Sub backplane.
Q9: "How does carpool corridor matching work mathematically?"
Answer: The driver's intercity road vector polyline $R$ is expanded into a 5,000-meter buffer polygon: $\text{Corridor} = \text{ST\_Buffer}(R, 5000)$. A passenger ride request is matched if and only if both the passenger pickup and dropoff coordinates are contained inside the corridor polygon: $\text{ST\_Contains}(\text{Corridor}, P_{\text{pickup}}) \land \text{ST\_Contains}(\text{Corridor}, P_{\text{drop}}) = \text{TRUE}$.
Q10: "How do you prevent driver GPS spoofing?"
Answer: Location updates are authenticated via JWT. The server verifies that the sending user possesses the driver role and is strictly assigned to the target ride (ride.driverId === user.id). Telemetry sent for unassigned, completed, or cancelled rides is immediately rejected.
